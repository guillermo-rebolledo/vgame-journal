## Detection and alert routing

1. Operations owner selects one existing alert destination, names primary/backup responders, and records access, timezone coverage, acknowledgement/escalation expectations and a restricted evidence pointer. Prefer existing Vercel/native provider alerts. Inspect entitlements before configuring; Vercel anomaly alerts can require a paid add-on. A paid plan or new paid service needs a separate owner decision.
2. Configure public entry `/` and bounded public application read `/api/health`. Every five minutes, check HTTP success **and a stable expected marker**, with a bounded timeout. Alert after two consecutive failures; keep one open incident per environment/check and emit one recovery on health. A 200 error/maintenance page, redirect to sign-in, missing marker or timeout is failure. Use the unauthenticated Home marker `Track what you’re playing` from its introduction (no session cookies) and the health JSON marker `"status":"ok","service":"shelve.games","version":1`. Require status 200 as well as the marker; the bounded health failure response has neither that marker nor service details. Never point a load tool at production.
3. Check durable daily task success independently, even when cron HTTP is 200. After 30 hours without success (or 30 hours after first deployment when no baseline exists), alert for each enabled Wishlist/Discovery task separately. Successful zero items is healthy; failed, skipped or running attempts never reset success age. Preserve prior snapshots and prior success timestamps during outages. Missing tasks, invalid/future timestamps, malformed health responses and monitor execution gaps are monitor failures, not healthy states.
4. Use one incident key per environment and bounded operation/task name; persist monitor state outside ephemeral workers. Expected validation/ownership rejection is separate from unexpected failed saves, server/render exceptions and account-email delivery failures. #144 supplies safe instrumentation; #135 supplies sanitization. Alert fields: operation, deployment alias/identifier, UTC timestamp, opaque safe correlation id, bounded error code and transition. No bodies, private notes, feedback, raw emails, passwords, headers, tokens, Calendar paths or complete URLs. Provider bounce/delivery failure routing must distinguish API acceptance from mailbox receipt; #141 owns real inbox verification.
5. Verify the destination with a synthetic incident, repeated failures and recovery. Save delivery/acknowledgement/resolution timestamps and a sanitized incident reference. The local drill below demonstrates a local receiver only. A screenshot of a configured monitor is not proof of delivery.

## Interfaces to sibling implementations

Integration `7c34145` includes #143. #143 owns all production durable health, cron and schema work. This branch adds no endpoint, scheduler, dashboard rule or application dependency. The public read and marker contracts are implemented below; real monitor configuration/delivery remains an operator task.

- Public cheap read: `GET /api/health` executes `SELECT 1` through the existing 10-second database transport deadline, with a 15-second handler budget. HTTP 200 returns exactly `{status:"ok",service:"shelve.games",version:1}`; database failure returns HTTP 503 with `{status:"unavailable"}`. Both are no-store. It returns no secrets/config/user data and performs no provider fetch or table scan. The public Home check separately requires HTTP 200 and its introduction marker above. Readiness must not become a high-frequency refresh operation.
- Protected freshness source: at integration `7c34145`, `GET /api/cron/refresh-health` uses the existing `CRON_SECRET` bearer protection and `Cache-Control: no-store`. It returns 200 when all required tasks are fresh/pending within grace, 503 when stale, and a bounded `{healthy:false,code:"refresh_health_unavailable"}` on read failure; unauthorized is 401. The JSON contains `healthy`, `evaluatedAt`, `thresholdHours:30`, `tasks` and `invocation`. Required tasks are `wishlist`, `recent`, `popular`; each has `enabledAt`, nullable `lastSuccessAt`, attempt/start/finish/outcome fields and `freshness` (`healthy`, `pending`, `stale`). Missing baseline is stale; the boundary is age ≥30 hours. Use these per-task persisted baselines, never a monitor restart time. This source is not an unauthenticated public liveness endpoint. The current persisted outcome is nullable before a first attempt, then `running`, `success`, `partial` or `failure`; skipped invocation evidence is `daily.lastSkippedAt`, separate from the running/success outcome. There is no enabled boolean in this schema: the three fixed daily task keys are required, and `enabledAt` is their persisted migration baseline. An external adapter must preserve those per-task baseline times and treat each current key as enabled, rather than inventing a new baseline when it restarts. Monitor authenticates through a secret store; credentials never enter evidence or the command line. Expected Wishlist plus every enabled Discovery selection must be present. The tools' `staleTasks(tasks, baselineAt, nowMs)` takes `{key, enabled, lastSuccessAt}` normalized by an adapter; it is an evaluator, not a production integration. `observe(previous, healthy)` returns bounded state and a transition; the scheduler/destination adapter owns durable state, delivery retries/acknowledgements and idempotency keys. Do not mark an incident delivered merely because this evaluator returned it.
- Protected cron: keep current consumer fields while adding bounded `success`/`partial`/`failure`/`skipped` outcomes. Required-subtask failures, including returned values, must cause non-success HTTP. #143 tests durable successful/empty/skipped/partial/failed behavior and lease exclusion. At integration `7c34145`, partial/failure returns 503, success/skipped returns 200. A skipped response is not proof of freshness; reread the protected health source. The old `91310e0` HTTP 200 contract did not establish success.
- #144 safe logging covers unexpected server/render, Journal write and email provider failures. Catalog/provider/dependency resilience is a sibling application slice; #145 only documents and exercises external seams. #140 owns atomic Journal retry correctness; the capacity harness additionally checks exported records under concurrent use.

## Scheduled refresh response

Repository schedule at `91310e0`: `0 6 * * *`, daily 06:00 UTC in `vercel.json`; protected `GET /api/cron/refresh-release-dates`; `maxDuration=180`. The scheduled work shares one 90-second deadline across Wishlist batches and both Discovery selections, within the 180-second handler budget. The remaining budget is reserved for bounded database requests and recording failure outcomes; provider results arriving after cancellation are ignored before new writes start. Each release-date replacement uses the existing transactional batch so insertion failure retains the prior dates. The database lease blocks another attempt for five minutes after acquisition (`nextAttemptAt`, `src/lib/catalog.ts`), including immediate retries after a failed invocation. Source rechecked at `7bea881`; actual hosted runtime entitlement remains an operator check.

Catalog operator inspects the named failed tasks, last successful timestamps, deployment and provider status/429s. Preserve last-good Discovery/Catalog data. Do not treat a legitimately unknown release as provider failure. Do not rely on Vercel retries: [cron management](https://vercel.com/docs/cron-jobs/manage-cron-jobs) documents that failed cron jobs are not retried. If safe, an authorized operator can rerun the protected GET once after the persisted lease expires using an approved secret-injecting client. Do not paste the bearer token into a shell transcript. Verify HTTP **and** every returned required-subtask outcome, then reread durable per-task success. If failures persist, stop reruns, keep stale detection active, and investigate quota/deadline rather than amplifying demand. Do not clear or bypass the lease.

## Application recovery

Release operator performs these steps; database operator joins when schema/data are involved.

1. Acknowledge the alert; record UTC detection/start, deployment alias, failure codes, affected operations and incident owner. Pause unsafe releases/automatic promotions using the existing release process. Read-only inspection precedes changes. Provider-wide outages may need bounded degradation/forward fix rather than code rollback.
2. Identify previous **known-good**, eligible deployment from restricted release history and its smoke evidence; record both commit IDs and migration sets. Verify that the operator's production role can perform rollback; access is a pending human check, not an assumed permission.
3. Compare migrations already applied to the schema the old code expects. Production builds apply migrations before old traffic stops. Additive changes can preserve compatibility; dropped/renamed columns, changed constraints/data semantics or noncompatible defaults can make rollback unsafe. Application rollback does not undo migrations, restore deleted rows or recall emails. Never run down migrations by guesswork. Prefer a compatible forward fix if uncertain; use #132 only for exceptional data recovery with explicit authorization.
4. Check old build's environment variable names/versions, valid credentials, runtime, cron definitions, provider API compatibility and eligible domains. [Vercel rollback](https://vercel.com/docs/instant-rollback) restores an earlier build/configuration; project-setting edits do not rebuild the old deployment. No DNS changes or credential rotation are authorized by this runbook.
5. In an isolated project with synthetic data first, deploy known-good A, write synthetic Journal/Playthrough records and record an export digest/count, deploy bad B with a deliberately broken marker, and record actual alert delivery. Use the host's rollback controls to recover A. Keep app/schema versions compatible and outbound mail/analytics/cron/providers isolated. Record elapsed time from detection to verified recovery and the achieved recovery point (last retained synthetic write), not a promised RTO/RPO. The local model is rehearsal support, not this hosted result.
6. Smoke Home, Catalog search, Library, Wishlist, game page, sign-in, Journal save/retry and export against synthetic accounts; compare record counts/digest and ensure no lost/duplicate writes, intact Playthroughs/drafts, unavailable versus empty behavior, and retained Catalog/Discovery snapshots. Verify durable freshness and a single recovery notification. #141 consumes this evidence. Production smoke must be bounded and explicitly operated, never a stress test.
7. Record incident cause, failed/passed checks, actual timing, recovery point and follow-up owners. Vercel rollback can stop automatic domain assignment; deliberately verify/unpause normal release promotion only after the forward fix is proven. Do not declare restored data based on restored code.

Database restore authority is [#132](https://github.com/guillermo-rebolledo/vgame-journal/issues/132), with its [security operations checklist](https://github.com/guillermo-rebolledo/vgame-journal/blob/3795133/docs/security-operations.md#backups-and-isolated-restore-exercise-operator-only). That checklist owns retention, restore destination/access, deletion handling, relationships, recovery timing and teardown. As reviewed 2026-11-09 it explicitly says no restore was performed; a verified isolated restore evidence link remains pending with the database operator. Follow it; do not create a second backup policy. Before any exceptional restore, assess writes since the recovery point and obtain explicit authorization. Never restore production under #145.

## Repeatable isolated checks

From repo root, after `pnpm install --frozen-lockfile`:

```sh
node --test tools/operations/*.test.mjs
node tools/operations/drill.mjs
OPS_GAMES=100 OPS_USERS=5 OPS_ITERATIONS=20 pnpm exec playwright test --config tools/operations/playwright.config.ts
```

The drill binds an ephemeral numeric loopback server; bad-build/known-good switches, stale task and receiver are synthetic. It checks repeated failures deduplicate and both incidents recover. Its elapsed milliseconds and retained one-record model are not Vercel rollback/Neon restore evidence. No five-minute wait is required to test the state machine; controlled time tests exercise the 30-hour boundary.

The performance configuration starts fresh Next production-mode E2E build/server on 127.0.0.1:3410 plus migrated in-memory PGlite/mail service on 3411. Ports must be free; it refuses server reuse, any `DATABASE_URL` and `VERCEL_ENV=production`. Do not pull production env. Browser outbound requests are blocked; provider/mail aliases and synthetic environment are fixed. It never accepts a remote staging or production target. Do not run simultaneously with another `.next-e2e` build. Tests never hit Neon. No screenshots, traces, HTML reports, cookies or exports are saved. Next/fixture diagnostic output contains synthetic context only; do not copy arbitrary production logs into this workflow.

Run the full local matrix, one fresh server per cell:

```sh
for games in 0 100 1000; do
  for users in 5 20; do
    OPS_GAMES=$games OPS_USERS=$users OPS_ITERATIONS=20 pnpm exec playwright test --config tools/operations/playwright.config.ts || break 2
  done
done
```

Each user has a distinct synthetic account and starting Journal, mixed Statuses, and three Playthroughs for every Played/Playing game (0/150/1500 Playthroughs at 0/100/1000). Each user navigates Home, provider-fixture-backed Catalog search, Library, Wishlist and game page, then saves and verifies an exported game/status without persisting the export. The empty Journal becomes one game after its first save. Five or twenty users run concurrently, with sequential journeys per user. Library assertions use settled data; save correctness uses public HTTP export, not direct SQL inspection. Seed SQL uses existing isolated support fixtures only.

JSON in `test-results/operations-reports/capacity-{games}-{users}.json` records revision, timestamps, dataset, concurrent users, raw samples, HTTP request/error counts and per-operation/mode attempts/errors/min/max. p50/p95 use nearest rank only with 100 successful samples per cell; fewer samples stay null. Failure samples are counted separately and never hidden by success percentiles. Preserve reports after reviewing for safe content; later same-cell runs overwrite this diagnostic file. Browser routing disables HTTP cache (installed Playwright type documentation); warm here means repeated application/server-cache journeys, not a browser HTTP-cache benchmark. Setup/signup/seeding is excluded; elapsed samples include full navigation readiness, menu interactions and save export verification, so they are journey latency, **not** isolated server/query latency. HTTP counters cover browser traffic, not setup or export API traffic. Caught failures remain counted; setup/assertion failures make the run fail.

`first-navigation` is reported separately from warm navigation and 390×844 slow-network navigation (150ms emulated latency, 1.6Mbps down/750kbps up). Browser-cache condition is not a hosted function/Neon cold start. Reports deliberately mark provider calls, DB usage, hosted cold starts and field vitals null. Local results cannot establish production capacity, app-wide quota behavior or a hosted two-second server-read budget.

Performance owner must additionally run the same dataset/user matrix in an **approved isolated hosted staging project**, using its approved authenticated journey runner/fixtures (not weakening this loopback guard). Record deployment/region/runtime, actual cold first invocation after verified process/compute idle/restart, warm cached page-data reads, provider-backed search, save acknowledgement separately from export verification, request count, errors, calls/429s across instances, DB CPU/connections/storage/query usage before/after, p50/p95 and the first limiting resource. Match dataset/environment across optimization comparisons. Record missing telemetry as pending; never infer zero calls from absent instrumentation. Do not add shared quota infrastructure or raise limits without measured need.

Provisional budgets from #139: warm staging save and cached page-data read p95 ≤2s at 5 users, with no lost/duplicate writes. Report search/cold separately; 20 users explores capacity, not a claimed supported limit. With sufficient field samples, [Core Web Vitals](https://web.dev/articles/vitals) p75 goals are LCP ≤2.5s, INP ≤200ms, CLS ≤0.1. Synthetic navigation is not field INP/LCP/CLS evidence. Stop on failure, inspect the first limiting resource and preserve results before making changes.

## Player freshness and telemetry safeguards

Wishlist reads persisted task evidence alongside Journal data. A failed check, stale success, absent successful baseline, or unavailable health read shows the existing tonal notice: release dates may be out of date, unannounced dates may not have been checked recently, and checks resume automatically. It keeps the known dates and unannounced group intact. A healthy successful check with genuinely unknown dates shows the normal unannounced label; an empty Wishlist omits the notice. This explanation never exposes provider errors or asks a player to run the operator-only refresh.

Scheduled and unexpected-error events share a safe envelope: validated deployment/commit metadata, timestamp, correlation id and bounded operation/outcome/code. JSON logging is best effort; a logging transport failure cannot stop task execution or turn persisted success into failure. The external monitor destination and delivery remain operator-owned pending evidence.
