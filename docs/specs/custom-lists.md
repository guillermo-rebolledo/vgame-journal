## Problem Statement

Players can record games in their Journal and share their public profile, but cannot curate collections such as “Games to play with friends,” “My favorite RPGs,” or “Next holiday.” Journal Status answers whether a game is Played, Playing, Backlog, or Wishlist; it does not express these personal groupings. Players need to organize games independently of their Journal and choose whether each collection is public or visible only to its creator.

The app also needs a concrete first social content type with clear authorship, stable links, and consistent visibility rules, so later social features can build on reliable ownership and privacy behavior.

## Solution

Introduce Custom Lists: named, ordered collections of Catalog games, owned and edited by one user. A list has an optional description and exactly two visibility choices: Private, visible only to its creator, and Public, readable by anyone, including signed-out visitors.

Users manage their lists from a Lists destination, add games through Catalog search or a game page, arrange their order, and share public lists through stable links. Public lists also appear in a Lists view on the creator’s existing public profile. New lists default to Private; publishing is an explicit choice.

This release establishes shareable content and access rules. It does not add a social feed or interaction system.

## User Stories

1. As a signed-in player, I want a Lists destination, so that I can find and manage my custom collections.
2. As a new list creator, I want an empty state with a clear create action, so that I know how to begin.
3. As a list creator, I want to name my list, so that its purpose is understandable.
4. As a list creator, I want an optional description, so that I can explain my selection.
5. As a list creator, I want new lists to default to Private, so that unfinished ideas are not published accidentally.
6. As a list creator, I want clear Public and Private explanations, so that I understand who can read my list.
7. As a list creator, I want to save an empty list, so that I can curate it over time.
8. As a list creator, I want to rename a list and edit its description, so that it can evolve.
9. As a list creator, I want separate lists with the same name to remain distinct, so that titles do not constrain my organization.
10. As a list creator, I want to search the Catalog from my list, so that I can add games without first recording them in my Journal.
11. As a list creator, I want search results to identify each game with its title, cover, and available platform information, so that I can choose the correct game.
12. As a list creator, I want helpful loading, no-results, and retry states for search, so that temporary problems do not interrupt curation.
13. As a list creator, I want to add a game to a list from its game page, so that I can collect recommendations as I browse.
14. As a list creator, I want the game-page picker to show only my lists and their visibility, so that I choose the right destination.
15. As a list creator with no lists, I want the picker to lead me through creating a list while retaining the selected game, so that I can complete the original action.
16. As a list creator, I want the same game in several different lists, so that collections can overlap.
17. As a list creator, I want an already-added game to be identified and duplicate submissions to avoid duplicate entries, so that each list stays coherent.
18. As a list creator, I want newly added games appended to my saved order, so that earlier curation is preserved.
19. As a list creator, I want to move a game to another position, so that I can express a sequence or preference.
20. As a keyboard or touch user, I want ordering controls that do not require dragging, so that I can arrange every game.
21. As a list creator, I want to remove a game from a list, so that I can revise its contents.
22. As a player, I want list membership changes to leave my Journal Status, Completion tags, Playthroughs, Wishlist, Countdowns, and Stats untouched, so that organizing games does not rewrite my gaming history.
23. As a player, I want games to remain in lists when I remove them from my Journal, so that curation is independent of tracking.
24. As a list creator, I want my list overview to show visibility, game count, cover previews, and last update, so that I can recognize and manage collections.
25. As a list creator, I want to make a private list public, so that I can share it when ready.
26. As a public list creator, I want a stable link that survives title edits, so that previously shared links keep working.
27. As a public list creator, I want to copy its public URL with accurate feedback and a manual-copy fallback, so that sharing works when clipboard access fails.
28. As a signed-out visitor, I want to open a public list without registering, so that a shared recommendation is immediately useful.
29. As a public list reader, I want to see its title, description, creator, ordered games, game count, and update date, so that I understand the collection.
30. As a public list reader, I want links to the creator’s profile and each game, so that I can explore further.
31. As a profile visitor, I want a Lists view containing only that creator’s public lists, so that I can discover their collections.
32. As a visitor, I want a clear empty state when a profile has no public lists, so that I know there is no public content to browse.
33. As a private list creator, I want my private lists absent from public profile cards, counts, response payloads, and previews, so that their existence and contents are not disclosed.
34. As a private list creator, I want another signed-in user or someone with a copied URL denied access, so that Private actually means creator-only.
35. As a public list creator, I want to make my list private again, so that future public reads stop exposing it and it disappears from my public profile.
36. As a list creator, I want only my authenticated account to edit, reorder, publish, or delete my lists, so that another user cannot change my content.
37. As a list creator, I want confirmation before deleting a list, so that I do not accidentally lose curation.
38. As a list creator, I want deleting a list to remove its entries and shared page while preserving Catalog games, other lists, and my Journal, so that deletion affects only the intended collection.
39. As a list creator, I want validation and failed-save messages to retain my input, so that I can correct or retry without retyping.
40. As a list creator using multiple tabs, I want a stale edit to be reported instead of silently overwriting newer changes, so that I do not lose curation or unintentionally republish a list.
41. As a player whose session expires or changes, I want saves to require the correct account and preserve recoverable input, so that I do not write into another account.
42. As a signed-out player selecting a list creation action, I want authentication and username onboarding to return me to that action, so that I can continue with context.
43. As a player with many lists or games, I want usable pagination and stable navigation, so that curation and reading remain manageable.
44. As a mobile, keyboard, or assistive-technology user, I want labeled controls, visible focus, announced outcomes, and layouts that handle long text and missing covers, so that the feature is usable throughout the app.
45. As a player exporting my account, I want both public and private lists with their saved game order included, so that my curation is portable.
46. As a player deleting my account, I want all of my lists and their entries removed while other players’ data remains, so that account deletion remains complete and isolated.

## Implementation Decisions

- **Scope and terminology.** Custom List and List Entry are distinct concepts from Journal Entry. A list is a curated collection, not a new Journal Status or a saved Library filter. One list belongs to one existing authenticated user; no collaborations or ownership transfer. Private-by-default, manual ordering, and the limits below are proposed product defaults synthesized from this request rather than features already implemented.
- **Existing foundation.** Reuse Better Auth identity and immutable, case-insensitive usernames; the local Catalog and its existing GameSource search; session-checked server actions; read-only public profile conventions; existing collection pagination, cover fallbacks, and clipboard behavior. Keep the Journal’s explicit public-field allowlist intact. No new identity provider, search provider, or social framework is needed.
- **Persistence.** Add a list entity with an opaque stable ID, creator foreign key, title, description, visibility, created/updated timestamps, integer revision, and a creation submission key unique within its creator. Add list entries referencing the list and Catalog game, with persisted order. Enforce a unique list/game pair, valid visibility values, nonempty bounded titles, and appropriate foreign keys at the database boundary. Cascade list deletion to entries and account deletion to lists. Do not reference Journal Entries from List Entries. Index owner listing and list-entry reads. Generate and review a migration using the established Drizzle workflow; no data backfill is needed.
- **Validation.** Trim titles and require 1–100 characters; descriptions are optional plain text up to 2,000 characters. Preserve description line breaks, render text safely, and do not interpret HTML or Markdown. Allow duplicate list titles and empty lists. Validate all action inputs at runtime, including IDs, visibility, text limits, revision, and reorder membership. Game additions must resolve to actual local Catalog records through the existing Catalog boundary; never trust client-supplied titles, covers, or owner IDs.
- **One cohesive list service.** Introduce a database-injected Lists service following the existing Journal factory pattern. Expose owner collection/detail reads; public collection/detail reads; and create, edit, visibility change, add/remove game, reorder, and delete operations. Centralize ownership, visibility, validation, and list invariants here. Avoid scattering authorization across components or introducing a generic social-content abstraction.
- **Trusted caller boundary.** Every server mutation re-reads the current session and obtains the actor from it. Never accept a submitted owner ID as authority. An expected actor ID may detect a switched account, as existing actions do, but cannot grant access. Service mutations additionally scope the target list to that actor; actions and pages remain thin adapters. Return structured validation, authentication, not-found, and conflict outcomes suitable for accessible UI messages; do not expose database errors or private content in failures.
- **Public reads are a separate projection.** Public detail reads require Public visibility and the matching creator; public collections filter before computing totals, preview covers, or serialized data. Return only explicit fields needed to render the list, creator attribution, and Catalog games. Do not join private Playthrough notes, email, credentials, feed tokens, or other account secrets. Never send a creator’s complete private list collection to a public profile component and hide it client-side. The public profile’s Lists view uses the same public list query as other public discovery surfaces.
- **Navigation contract.** Use `/lists` for the signed-in creator’s overview and creation entry point, and `/lists/[listId]` for creator-only list detail/editing. Use `/u/[username]/lists/[listId]` as the canonical public sharing route. Add `Lists` to collection navigation and `?view=lists` to the existing public profile view switcher, preserving other URL state. An owner detail page links to its public version when Public. The public route always applies public visibility rules, including for the owner; owners manage private content through the owner route.
- **Missing and unauthorized content.** Unknown IDs, malformed IDs, wrong-creator public URLs, deleted lists, and nonpublic public URLs produce the same generic not-found result without list title, description, games, or revealing error text. Signed-in nonowners cannot read owner routes. Signed-out owner routes use the existing safe sign-in continuation. Ensure real HTTP 404 behavior for inaccessible public list navigation before a private-content stream starts; the existing profile preflight currently recognizes only the profile root and needs an explicit decision for nested list routes.
- **Creation and editing.** A creation form offers title, optional description, and clearly explained visibility with Private selected. Explicit submission may create either visibility, including an empty public list. Persist successful mutations before announcing success. Provide explicit metadata save, clear pending states, retained input on failure, and confirmation before deleting. The overview is ordered by latest update with stable ID tie-breaking. List cards show an explicit visibility label in owner views, count, a small ordered cover preview, and last update; public profile cards never imply hidden private counts.
- **Game selection and independence.** The list editor reuses the existing game-search behavior, identifying and disabling already-added games. A game-page Add to list picker shows only the actor’s lists, marks existing membership, and supports creating a list while retaining the selected Catalog game. Additions append; removals affect only that list; the same game may appear in any number of distinct lists. Selecting a list never implicitly saves a Journal Status or Playthrough. Public pages load their existing Catalog data even when external game search is unavailable.
- **Ordering and concurrency.** Persist a creator-defined order and use it on every reading surface. Offer Move up/Move down controls with accessible game-specific labels; dragging is optional. Moves must work across pagination boundaries, preserve membership, and keep focus on the moved game or its resulting page. Check the expected list revision on updates, including publication changes, membership, ordering, and deletion. Apply each effective mutation, revision increment, and timestamp update atomically. Reject stale changes with a refresh/retry path rather than overwriting newer data. Deduplicate repeated additions and avoid duplicate lists from an uncertain create retry, using a stable creation submission key scoped to the actor. Use the existing database batching/locking approach or a single conditional statement compatible with Neon HTTP and PGlite; do not assume interactive production transactions are available.
- **Privacy and caching.** Private means creator-only, including to other authenticated users and users who possess its URL. There is no unlisted or friends-only mode. Visibility changes preserve list identity, games, and order. Once a Public-to-Private mutation succeeds, all newly initiated public reads must apply the current policy, including profile lists, counts, metadata, and any preview endpoint. Keep visibility-sensitive data request-time and out of persistent shared caches for this release; a cached static shell must contain no private list data. Prevent browser/shared response caching of list data and refresh affected owner/public views after successful mutations. Client state must not carry owner-only collections across account changes. Content already downloaded by someone or retained by an external preview service cannot be recalled; the app must not promise otherwise.
- **Sharing and metadata.** Public URLs use the stable list ID, so title changes do not break links. Show the canonical public URL with a selectable field and clipboard success/failure feedback only when Public. Extend the existing clipboard component’s context and copy rather than displaying Calendar-specific fallback text for lists. Public list metadata includes the title, creator, a bounded description, and canonical URL only after authorization; private/missing list routes use generic metadata and a noindex policy. Use the generic site share image initially; do not create a new generated list-cover system. Keep owner pages out of crawling and keep lists out of the global sitemap, consistent with the existing choice not to create a public member directory. Robots directives are supplementary and never substitute for access checks.
- **Collection UX.** Reuse existing URL pagination behavior for owner lists, public profile lists, and list games, with distinct page parameters and clamping after deletion. Public reads remain read-only. Provide loading, genuine empty, unavailable, and retry states; a failed read must not look like an empty list. Handle unavailable artwork and long text. Support narrow phones, both themes, visible keyboard focus, meaningful labels, announced errors/success, and existing reduced-motion preferences. Avoid introducing a new design system.
- **Account lifecycle.** Extend authenticated account export additively with the actor’s lists, visibility, timestamps, and ordered game identifiers plus useful Catalog titles/slugs. Include private lists only in that actor’s export. Verify the deletion cascade removes lists and entries without deleting shared Catalog games or anyone else’s data. This does not add import support or alter existing exported fields.
- **Future social foundation.** Stable list identity, creator attribution, revisioned mutations, and centralized public projections are the extension points for future likes, comments, saves, and feeds. Do not add unused interaction tables, follower graphs, polymorphic content registries, generic permission engines, event buses, counters, or notifications in this release. A future interaction or feed feature must recheck the current visibility of the referenced list rather than treating an earlier public snapshot as permanently readable.

## Testing Decisions

- Good tests exercise observable contracts and user outcomes: who can read or change a list, what is persisted, what public responses contain, and whether the creator can recover from a failure. Avoid SQL-string assertions, private helper tests, mirrored implementation logic, and snapshots of internal structures.
- The **primary feature acceptance seam is the existing production-build Playwright app boundary**, using the existing isolated PGlite support server, fake GameSource, mailbox, and real authentication flow. Extend this harness rather than creating a separate browser stack or testing against Neon. Existing public-profile/account-lifecycle journeys and collection/search recovery journeys are the closest prior art.
- Cover complete workflows with separate contexts for creator, unrelated signed-in user, and signed-out visitor: create Private; add a Catalog game absent from the Journal; add another game from its page; prevent duplicate membership; order/remove entries; publish; visit copied URL and public profile; edit without changing the URL; unpublish; verify new visitor reads fail; republish; delete; verify the URL disappears. Verify public profile counts/previews change with visibility and never reveal a private list.
- Test privacy on raw HTML, server-component/navigation payloads, document metadata, and relevant image/data responses, rather than merely asserting hidden DOM. Use distinctive private title/description/game selections; verify anonymous and unrelated signed-in reads cannot obtain them, including after a previously public list becomes private. Check actual HTTP status for direct inaccessible list navigation and generic metadata. Exercise direct unauthorized mutation requests so hiding edit controls cannot satisfy the access-control tests.
- Add focused database-backed contract tests at the **single new Lists service boundary**, using `createTestDb()` with real migrations, following existing Journal ownership/public-projection tests. Cover server-side validation, unique membership, overlapping lists, order persistence, malformed/wrong-owner IDs, public allowlists, atomic failure, creation retries, concurrent/stale mutations, and visibility changes. Reuse account export/deletion contract tests for lifecycle assertions. These target combinations and races that are expensive or nondeterministic through a browser; do not repeat every workflow at every layer.
- Verify failure recovery for unavailable search, failed/ambiguous mutation responses, expired/switched sessions, stale revisions, and clipboard denial. Retry must not create duplicates or silently overwrite changes. Include concurrent publication/edit tests to prevent an old edit from republishing a newly private list.
- Use browser acceptance checks for narrow layouts, keyboard-only creation/editing/ordering, cross-page reordering, focus after removal, list pagination with Back/Forward/reload, long titles, missing covers, empty public lists, and a profile with only private lists. Add component tests only for an interaction with a meaningful inaccessible browser edge case; do not create another default acceptance seam.
- For implementation, run lint, type checking, relevant Vitest modules, and focused Playwright acceptance journeys using the repository’s commands. Check the migration through the existing test database setup. This specification/research task itself changes documentation only and does not require running application tests.
- **Agreed testing approach:** the user confirmed existing Playwright journeys as the primary acceptance seam, plus focused Lists-service tests for privacy, persistence, and concurrent edits using the existing in-memory Postgres/PGlite factory. The required to-spec seam review is complete.

## Out of Scope

- Following/followers, friend graphs, feeds, notifications, mentions, messages, social login changes, and profile redesigns.
- Likes, comments, bookmarks/saves of other people’s lists, list cloning, collaboration, and ownership transfer.
- Global list search, trending/recommended lists, a public member directory, and exposing lists on every game’s community page.
- Unlisted, friends-only, follower-only, Personal, or account-wide privacy modes. This feature does not change visibility of the existing public Journal/profile.
- Formal ranked/unranked modes, progress tracking, completion percentages, list analytics, and per-game list notes. Manual ordering is included; ranking semantics and new progress calculations are not.
- Folders, tags, rich text, custom cover uploads, embeds, importing lists, and bulk Journal operations.
- A new reporting/moderation dashboard or automated moderation platform. Continue existing feedback/support access; adding wider discovery or user interactions needs a separate moderation decision.
- Building speculative social infrastructure or implementing Backloggd feature parity.
