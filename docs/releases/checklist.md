# Release verification (#141)

Copy [the evidence record](evidence-2026-11-09.md) for each candidate. A release owner must replace role placeholders with people, identify the immutable deployment and commit, and sign the decision. Preparing this process does not certify a production release. Supported baseline: current stable Chromium, Firefox and desktop Safari; current iOS Safari and Android Chrome for core flows. Record actual OS/browser versions, not just “latest.” Playwright WebKit is engine coverage, not actual Safari/iPhone evidence.

## Evidence rules and release decision

Each result must have: responsible person, UTC date, environment, deployment/commit, prerequisite, action, expected outcome, actual outcome, sanitized evidence reference and **pass / fail / pending**. The checklist IDs below supply prerequisite/action/expected outcome; the release record supplies the remaining fields. Inherited metadata is allowed only when stated explicitly. Pending always has an owner and next action. Keep raw exports, mailbox addresses, recovery links, credentials, callback/Calendar tokens and identifiable provider screenshots in a restricted location. Public references must be sanitized aliases, never live token URLs. Use designated synthetic accounts; deletion uses a separate disposable account. Keep a non-destructive monitor account if needed.

Stop release for failing/skipped/cancelled required checks; data loss/partial writes; broken auth/recovery; broken core save/edit in a supported browser; ownership/privacy regression; blocking accessibility defects; failed applicable migration rehearsal; or critical provider/device evidence pending. A human release owner records **release / hold** and the evidence used; agents cannot waive these conditions. Record defects against the owning issue, then rerun affected checks on the corrected candidate.

Reuse evidence only by citing its exact deployment/commit, unchanged area, date, result, and why it applies. Schema changes rerun migrations, old-artifact compatibility and persistence. Auth/provider/config changes rerun inbox/Google/security checks. Shared UI changes rerun affected browser/device/accessibility flows. Include exact #139 operations and #140 integrity revisions in each candidate; absent/unverified dependencies stay pending. Do not duplicate #137's detailed #130 security suite: reference its candidate-valid [acceptance](../security-acceptance.md) and [browser verification](../security-browser-verification.md), including #134 Google reauthentication/deletion.

## Migration and old-artifact rehearsal (database + release operators)

No schema change in this PR. A schema-changing candidate requires M01–M04 before release. The local regression freezes baseline `0018_account_security_privacy`, seeds representative users/sessions/Journal/history/Playthroughs/Ratings/Lists, then applies `0019` and later migrations. It checks retained records, old column-list writes, constraints, and transactional retry. This does **not** prove the old binary or Neon adapter works. For a newer baseline deliberately update the test/fixture together and retain a pending migration to exercise; never silently turn this into an empty upgrade.

Use an explicitly approved empty, disposable **nonproduction** database/project without production data; provisioning/access remains the database owner's task. Never clone production data for this drill. Use the existing Drizzle migration workflow and an operator-verified direct migration connection; keep the application's approved connection semantics/config. Do not print either connection string or pull production `.env.local`. Validate resource identity in the dashboard before enabling writes. Follow current Neon skill/docs if provisioning a new target is necessary.

1. **M01 baseline and seed:** identify previous known-good artifact/commit and its exact applied migration list. On a separate operator checkout of that revision, with its disposable target connection injected as `DATABASE_URL`, run `pnpm install --frozen-lockfile` and `pnpm db:migrate`. Start the baseline app on isolated resources and create/verify/onboard a controlled account through its normal auth flow. Keep its signed-in session; privately obtain that account’s internal ID through the authorized database client, matching its controlled username. With `PGDATABASE`/`PGHOST`/credentials securely configured for the **same disposable target**, set `RELEASE_USER_ID` to that ID and run `psql -v ON_ERROR_STOP=1 -v release_user_id="$RELEASE_USER_ID" -f src/test/fixtures/release.sql` from the candidate checkout. The psql variable is SQL-quoted by the fixture; it must reference that existing account, never an invented session. Use that same authenticated account for the old/new artifact checks, including `/games/synthetic-game` and export. Fixture requires baseline >=0018; adjust explicitly for older supported schema, never apply it blindly. Record baseline counts/digests and expected constraint checks. No personal data.
2. **M02 migration while old app serves:** start the known-good artifact with its original configuration names/versions pointed only at the disposable resources. Perform synthetic read/save/edit/export. From candidate checkout, inject the same verified direct target and run `pnpm db:migrate`. Before starting new code, repeat old-artifact reads/writes and compare export/record counts. Then start candidate with its isolated app configuration and repeat core journeys, relationships, constraints and persistence. Record both artifact SHAs and migration set. Expected: no lost/duplicate records and old/new both work on expanded schema. Application rollback does not reverse migrations.
3. **M03 failure and retry:** use a second fresh disposable target with the baseline data. In a disposable candidate copy append a deliberately invalid migration using Drizzle's normal generated migration/journal workflow. Run the production build sequence (`VERCEL_ENV=production pnpm build`) only with that target's direct `DATABASE_URL` and isolated app configuration; expect nonzero migration failure, no build/publish step and intact baseline data/migration ledger. Do not publish this artifact. Correct the unapplied migration in that disposable copy, retry per Drizzle's supported behavior and verify it applies once without lost records. If actual behavior differs, stop and investigate; never edit a successfully applied migration or invent down migrations. Local PGlite rollback test is only supporting evidence, not publication proof.
4. **M04 rollback:** follow [application recovery](../operations/runbook.md#application-recovery) with the last known-good artifact and its original isolated configuration against expanded schema. Verify old reads/writes, auth, export, task health and record digests; record timings and constraints. Exceptional database restoration belongs to #132, not this drill. Delete disposable targets and revoke temporary credentials after evidence capture; record cleanup.

Expected for all applicable M rows: recorded success on isolated production adapter/connection semantics, no production changes, no data loss and compatible old artifact. Missing access/artifact or failed drill means hold. For a code-only release, record why no pending schema change exists; configuration/provider changes still need their respective rows.
